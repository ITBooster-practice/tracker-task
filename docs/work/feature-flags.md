# Флаги функций

Флаги определяются в коде и переносятся между окружениями SQL-миграциями. Состояния хранятся в существующей БД приложения. На странице `/admin/feature-flags` [разработчик системы](../backend/system-developer.md) может только включать и выключать существующие записи.

## Что хранится

- `FEATURE_KEYS` содержит технические ключи.
- `FEATURE_REGISTRY` в [общем пакете типов](../../packages/types/src/feature-flags/registry.ts) описывает подключённые функции и их названия.
- `FeatureFlag` хранит `id`, уникальный `key`, `enabled` и технический `updatedAt`.
- `FeatureFlagsRevision` хранит общую версию для конфликтов записи, ETag и обновления клиентов.

Подключение вычисляется из реестра и не дублируется в БД. Реестр не анализирует исходники: запись добавляется вместе с реальными проверками. Новые флаги всегда создаются выключенными. Описания, авторы, сроки, архив и история отсутствуют.

## Добавление и подключение

1. Добавьте ключ в `FEATURE_KEYS`, проверки на API/frontend и название в `FEATURE_REGISTRY`. Для заготовки без проверок запись в реестре пока не добавляйте.
2. Создайте SQL-миграцию данных. Не меняйте применённые миграции и не используйте seed или синхронизацию при запуске вместо миграции.
3. Примените миграции и выпустите код на всех API и web. Затем включите флаг в нужном окружении.

Пример миграции нового ключа `new-section`:

```sql
BEGIN;
SELECT "id" FROM "FeatureFlagsRevision" WHERE "id" = 'global' FOR UPDATE;

INSERT INTO "FeatureFlag" ("id", "key", "enabled", "updatedAt")
VALUES (gen_random_uuid()::text, 'new-section', false, CURRENT_TIMESTAMP)
ON CONFLICT ("key") DO NOTHING;

UPDATE "FeatureFlagsRevision" SET "version" = "version" + 1 WHERE "id" = 'global';
COMMIT;
```

`ON CONFLICT DO NOTHING` сохраняет состояние существующей записи. Не сбрасывайте `enabled` при повторном выпуске.

Подключая существующую заготовку, добавьте реестр и миграцию с блокировкой/увеличением общей версии. Изменения подключения тоже меняют runtime-снимок: версия нужна для ETag и уведомлений.

Неподключённый ключ нельзя включить; его старое включённое состояние можно выключить. API и runtime-снимок не разрешают неподключённую функцию. Отсутствующий ключ также считается выключенным.

Примеры проверок: [API](../backend/feature-flags.md), [frontend](../frontend/feature-flags.md). Задачи требуют проектов; доски — проектов и задач.

## Удаление

Удалите проверки флага и ненужную ветку кода, оставив окончательное поведение функции. Удалите ключ из `FEATURE_KEYS` и `FEATURE_REGISTRY`. После прекращения поддержки версий с этим ключом удалите строку миграцией:

```sql
BEGIN;
SELECT "id" FROM "FeatureFlagsRevision" WHERE "id" = 'global' FOR UPDATE;
DELETE FROM "FeatureFlag" WHERE "key" = 'new-section';
UPDATE "FeatureFlagsRevision" SET "version" = "version" + 1 WHERE "id" = 'global';
COMMIT;
```

Не удаляйте строку, пока поддерживаемый код требует включённый флаг: оставшиеся проверки закроют функцию. Не переиспользуйте ключ для другой функции.

## Миграции и развёртывание

Миграции переносят **состав флагов**, а не выбранные состояния. В каждом окружении своя БД и собственные `enabled`. Новый ключ появляется выключенным; повторные деплои сохраняют существующие значения. Переключения через панель не создают миграций.

Любое добавление, подключение, отключение от кода или удаление сопровождайте миграцией с увеличением `FeatureFlagsRevision`. Значения меняйте через API/панель: прямой UPDATE обходит версию и уведомления.

Все экземпляры API используют одну БД, один Redis и одинаковый `SYSTEM_DEVELOPER_USER_ID`. SSE и сверка версии обновляют открытые клиенты. Backend проверяет состояние при запросе; отключение не отменяет начатую операцию.

Порядок применения миграций и требования к совместимости версий — в [руководстве Prisma](../backend/prisma/README.md#обновление-существующей-бд-без-потери-данных). Для локального контейнерного стека используйте [инструкцию local-stage](./local-stage.md).
