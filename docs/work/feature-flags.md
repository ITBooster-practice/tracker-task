# Runtime feature flags

Флаги хранятся в PostgreSQL и меняются без пересборки приложения и миграций для отдельных флагов. Миграция нужна только для изменения структуры таблиц. Права пользователей на данные продолжают проверяться отдельно.

Управлять флагами может только разработчик системы, чей существующий ID задан в серверной настройке `SYSTEM_DEVELOPER_USER_ID`. OWNER и ADMIN команды не получают этих прав. Если ID не задан, управление закрыто для всех. Настройка одинакова на всех API; её изменение требует перезапуска. [Настройка разработчика](../backend/system-developer.md).

## Работа в панели

1. Откройте **Флаги функций** в меню или `/admin/feature-flags`.
2. Создайте флаг: уникальный технический ключ, название, описание с планом завершения, состояние и необязательная плановая дата. Новый флаг по умолчанию выключен.
3. Добавьте проверки в коде. Создание записи само по себе не изменяет поведение блока.
4. Включайте и выключайте функцию в панели. Открытые браузеры получают SSE-уведомление и заново загружают snapshot.
5. Поиск и фильтры отделяют активные, включённые, выключенные и архивные флаги. **История** показывает автора, время и состояния до/после последних 100 изменений.
6. Если получен конфликт 409, список обновляется: проверьте свежие значения и откройте форму заново. Изменения другого клиента не перезаписываются автоматически.

Key неизменяемый и занят навсегда, включая архив. Название можно изменять и повторять. Для нового поколения блока используйте новый ключ, например `boards-redesign-v3`. Плановая дата не переключает флаг автоматически.

## Подключение нового блока

- Общие технические ключи и `REQUIRED_FEATURE_KEYS`: `packages/types/src/feature-flags/index.ts`. Добавляйте используемые поддерживаемым кодом ключи в реестр обязательных: API запретит их преждевременную архивацию.
- Backend: `@Authorization()` и `@RequireFeatures('new-block-v1')` на контроллере/методе; для сервисных операций используйте `FeatureFlagsService.requireEnabled`. Прямой запрос к API при выключенном/отсутствующем/архивном флаге получает 403 `FEATURE_DISABLED`.
- Frontend: `useFeature(key)`, `hasFeature(snapshot, key)` и `FeatureGate` для уже открытого UI; `requireServerFeature(key)` для серверной страницы/layout и прямого URL. Меню использует тот же snapshot.
- Зависимости функций задаются на обоих уровнях: tasks требует projects, boards требует projects и tasks.
- Покройте открытие URL, прямой API-запрос, переключение уже открытого блока, сетевую ошибку, отсутствие ключа и штатные права пользователя.

Backend проверяет БД при каждом запросе, без локального кэша. Redis Pub/Sub доставляет изменения между экземплярами API; каждый экземпляр сверяет версию БД каждые 5 секунд для восстановления потерянных уведомлений. Браузер восстанавливает SSE и cookie-сессию после разрыва. При ошибке загрузки snapshot UI закрывает функции и предлагает повторить запрос.

## Завершение выпуска и удаление временного кода

1. Включите функцию и подтвердите готовность для всех пользователей.
2. Удалите проверки этого ключа из UI, меню, страниц, API, сервисов и тестов; удалите старую ветку реализации. Сохраните авторизацию и проверки прав на данные.
3. Найдите оставшиеся ссылки, например `rg "boards-redesign-v3" apps packages`. Удалите ключ из реестра обязательных после очистки проверок.
4. Запустите проверки и выпустите очищенный код. Завершите поддержку старых образов и обновите старые открытые вкладки.
5. Архивируйте флаг через панель. Запись и история остаются; старый технический ключ нельзя создать повторно.

**Архивация не делает функцию постоянной:** оставшаяся проверка закроет блок. Постоянное поведение появляется после удаления проверки из кода. Повторное отображаемое название с новым key не влияет на очищенный блок.

## Rollout и эксплуатация

Примените миграцию `20261010000000_add_runtime_feature_flags`. Она создаёт четыре начальных флага включёнными; повторный migrate deploy не меняет их значения. Если старое окружение отключало функции env-переменными, перенесите эти состояния в БД до допуска пользователей к обновлённому приложению. Старые `NEXT_PUBLIC_FEATURE_PROJECTS/TASKS/BOARDS/TEAM_SETTINGS` больше не используются.

Проверьте: обычный пользователь не может управлять, разработчик может переключать, открытая вкладка меняется, прямой API даёт 403, потеря Redis восстанавливается сверкой БД. Через stage-proxy SSE должен работать без буферизации; при восстановлении соединения клиент получает текущую версию. При откате на старый frontend его env-флаги не дадут обхода нового backend; при откате backend вместе со старым frontend новая серверная защита исчезает, поэтому откат всего приложения требует отдельной проверки доступа.

Локальный `NEXT_PUBLIC_FEATURE_FLAGS_DEV_FALLBACK=true` разрешён только при `NODE_ENV=development`, отмечен предупреждением, не выдаёт права разработчика и не обходит API. Stage/production fallback не используют.

При ошибочном выключении откройте панель, обновите список и включите нужный флаг; при 409 перечитайте актуальные данные. Проверьте snapshot и прямой API-запрос, затем открытые вкладки. Архив восстановить нельзя: прежний ключ зарезервирован; завершайте очистку кода либо выпускайте новый ключ. Не редактируйте таблицы вручную: обход API не создаёт аудит и не увеличивает revision.

Проверка реализации (10.10.2026): API unit — 196, HTTP e2e — 117; web unit — 567. Порог покрытия 80% сохранён. Prisma migrate deploy повторён, diff схемы пустой; TypeScript, ESLint, API build и Next production build проходят. В production-сборке на изолированном локальном стенде проверены создание/изменение/архивация/история, запрет повторного ключа, обычный пользователь, мобильная форма и переключение открытой доски: UI закрывается, URL 404, API 403, повторное включение без reload. Доставка между двумя API и восстановление после потерянной публикации проверены e2e. Проверка через реальный stage Caddy выполняется при деплое.
