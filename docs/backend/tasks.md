# Модуль Tasks

## Обзор

Модуль управляет задачами внутри проекта. Каждая задача принадлежит проекту (`Project`), проект — команде (`Team`). Доступ к любому эндпоинту задач проверяется через членство в команде (`TeamMember`). Основная логика находится в [TasksService](../../apps/api/src/tasks/tasks.service.ts).

### Используемые Prisma-модели

| Модель                | Назначение                                                            |
| --------------------- | --------------------------------------------------------------------- |
| `Task`                | Сама задача: заголовок, статус, приоритет, позиция, исполнитель       |
| `TaskLabel`           | Справочник имён меток отдельного проекта                              |
| `TaskLabelAssignment` | Связь задачи с меткой внутри одного проекта                           |
| `Project`             | Проект, которому принадлежат задачи; связан с командой через `teamId` |
| `Team`                | Верхний уровень иерархии; через `TeamMember` определяются права       |

**Ключевые ограничения схемы:**

- `Task.projectId` → `Project.id` (`onDelete: Cascade`)
- `Task.position` — целое число, индексируется вместе с `projectId` и `status`: `@@index([projectId, status, position])`
- `Task.status` по умолчанию `TODO`; `Task.priority` по умолчанию `MEDIUM`
- `Task.assigneeId` и `Task.dueDate` — необязательные поля

## Маршруты Tasks

Базовый путь: `GET|POST|PATCH|DELETE /teams/:teamId/projects/:projectId/tasks`

Все маршруты защищены Bearer-токеном (`@Authorization()`).

Ответы создания, списка, деталей и обновления возвращают [Task](../../packages/types/src/tasks/types/task.types.ts) с обязательным `boardColumnId` — ID текущей колонки задачи.

| Метод    | Путь            | Параметры                                   | Коды ответа             |
| -------- | --------------- | ------------------------------------------- | ----------------------- |
| `POST`   | `/`             | body: `CreateTaskDto`                       | 201, 400, 403, 404      |
| `GET`    | `/`             | query: фильтры + пагинация                  | 200, 403                |
| `GET`    | `/board`        | query: обязательный `boardId`               | 200, 400, 403, 404      |
| `GET`    | `/labels`       | query: необязательный `search`              | 200, 400, 403, 404      |
| `GET`    | `/:taskId`      | path: `taskId`                              | 200, 403, 404           |
| `PATCH`  | `/:taskId`      | path: `taskId`, body: `UpdateTaskDto`       | 200, 400, 403, 404, 409 |
| `PATCH`  | `/:taskId/move` | path: `taskId`, body: `MoveTaskToColumnDto` | 200, 400, 403, 404, 409 |
| `DELETE` | `/:taskId`      | path: `taskId`                              | 204, 403, 404           |

## Маршруты Board

### `GET /teams/:teamId/projects/:projectId/tasks/board`

Передайте обязательный `boardId` в query, например `tasks/board?boardId=UUID`. Сервис проверяет принадлежность доски проекту и возвращает `BoardView = { board, columns }`. Количество колонок определяется выбранной доской, а не перечнем статусов.

Объект `board` содержит описание `description: string | null`. Каждая колонка содержит `id`, `key`, `title`, `color`, `isSystem`, `position` и массив `tasks`; задачи содержат `boardColumnId`, `version` и `labels: string[]`. Поле `color` принимает `gray`, `blue`, `cyan`, `green`, `yellow`, `orange`, `red` или `violet` по [boardColumnColorSchema](../../packages/types/src/boards/schemas/board.schema.ts); значения цветов обеих тем заданы в [палитре статусов и колонок](../design-system/README.md#палитра-статусов-и-колонок). Колонки и задачи внутри них упорядочены по `position`. Полный контракт — в [типах BoardView](../../packages/types/src/boards/types/board.types.ts) и [BoardViewResponseDto](../../apps/api/src/tasks/dto/board-view-response.dto.ts). Чтение доски и перемещение реализует [BoardTasksService](../../apps/api/src/tasks/board-tasks.service.ts).

## Права доступа

| Действие     | Минимальная роль    | Дополнительное условие                          |
| ------------ | ------------------- | ----------------------------------------------- |
| `create`     | `MEMBER`            | —                                               |
| `findAll`    | `MEMBER`            | —                                               |
| `findLabels` | `MEMBER`            | —                                               |
| `getBoard`   | `MEMBER`            | —                                               |
| `findOne`    | `MEMBER`            | —                                               |
| `update`     | `MEMBER`            | только `ADMIN`/`OWNER` **или** создатель задачи |
| `moveTask`   | `MEMBER`            | —                                               |
| `remove`     | `ADMIN` или `OWNER` | —                                               |

Проверка членства выполняется через `assertTeamMember` — ищет запись `TeamMember` по `{ teamId, userId }`. Если запись не найдена → `403 ForbiddenException`.

Для чтения, обновления и удаления задачи сервис также проверяет `Project.teamId` и `Task.projectId` по параметрам маршрута. Чужой или отсутствующий проект и задача другого проекта возвращают `404`. Назначение пользователю задачи само по себе не даёт права её редактировать: нужен создатель либо роль `ADMIN`/`OWNER`.

## Фильтры и сортировка (`findAll`)

Эндпоинт `GET /` принимает следующие query-параметры:

| Параметр     | Тип          | Описание                                                                                       |
| ------------ | ------------ | ---------------------------------------------------------------------------------------------- |
| `page`       | `number`     | Номер страницы (по умолчанию 1)                                                                |
| `limit`      | `number`     | Размер страницы (по умолчанию 10)                                                              |
| `status`     | `TaskStatus` | Фильтр по статусу: `TODO`, `BACKLOG`, `IN_PROGRESS`, `IN_REVIEW`, `DONE`                       |
| `priority`   | `Priority`   | Фильтр по приоритету: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`                                      |
| `assigneeId` | `string`     | UUID пользователя-исполнителя                                                                  |
| `type`       | `TaskType`   | `TASK`, `BUG`, `STORY`, `EPIC`, `TECH_DEBT`                                                    |
| `search`     | `string`     | До 255 символов; подстрока названия или имени метки без учёта регистра либо точный UUID задачи |
| `sortBy`     | `string`     | `createdAt`, `priority`, `status`; по умолчанию `createdAt`                                    |
| `sortOrder`  | `string`     | `asc` или `desc`; по умолчанию `desc`                                                          |

По умолчанию задачи сортируются по `createdAt DESC`. Второй ключ — `id` в том же направлении, чтобы порядок при одинаковых значениях был стабильным. Ключ задачи — её UUID `id`; отдельного номера нет. Поиск объединяет через OR подстроку названия и имени метки; если `search` имеет формат UUID, добавляет точное совпадение `id`. Все условия ограничены текущим проектом. Символы `%`, `_` и обратный слеш экранируются для буквального поиска.

Параметры валидируются через `taskFilterQuerySchema` (Zod). Непереданные фильтры игнорируются.

## Обновление задачи

`PATCH /teams/:teamId/projects/:projectId/tasks/:taskId` принимает частичный объект по [updateTaskSchema](../../packages/types/src/tasks/schemas/update-task.schema.ts), включая необязательный `boardColumnId`. Непереданные поля сохраняются; `assigneeId: null` и `dueDate: null` очищают исполнителя и срок, `labels: []` снимает все метки.

Чтобы изменить колонку вместе с названием, метками или другими полями, передайте их одним PATCH. `boardColumnId` должен указывать на колонку той же доски и проекта; колонка другой доски или проекта либо отсутствующая цель возвращает `404`. Задача перемещается в конец целевой колонки, порядок исходной уплотняется; версии задач с изменёнными позициями увеличиваются. Если цель совпадает с текущей колонкой, `position` сохраняется. Все изменения выполняются атомарно.

Системная цель задаёт `status` по своему `key`, даже если запрос содержит другой статус. Пользовательская цель сохраняет текущий статус либо принимает явно переданный `status`. Если передан только `status`, задача из системной колонки переходит в соответствующую системную колонку той же доски; задача из пользовательской колонки остаётся на месте.

Перед записью сервер читает задачу и использует прочитанную `version` в условии обновления, увеличивая её на 1. Гонка между этим чтением и записью даёт `409`: клиенту нужно обновить данные и повторить действие. Клиент не передаёт `expectedVersion` в этот PATCH, поэтому эта проверка не обнаруживает все изменения за время открытой формы. Преобразование полей формы и повтор запросов описаны в [frontend-сценарии задач](../frontend/task-workflow.md).

Общий [task-placement.ts](../../apps/api/src/tasks/task-placement.ts) пересчитывает размещение для PATCH и API перемещения. При расширении этих операций сохраняйте порядок блокировок: сначала затронутые доски, затем задачи; обновляйте задачу с проверкой версии.

## Метки задач и каталог проекта

Ответы CRUD задач и `BoardTask` всегда содержат `labels: string[]`, включая пустой массив. Создание и обновление принимают необязательный `labels: string[]`. При создании пропуск поля означает отсутствие меток; при PATCH пропуск сохраняет назначения, переданный массив полностью заменяет их, а `[]` очищает.

Правила задаёт [task-label.schema.ts](../../packages/types/src/tasks/schemas/task-label.schema.ts):

- Имя нормализуется в Unicode NFC, пробелы по краям удаляются, последовательности пробельных символов заменяются одним пробелом.
- После нормализации имя содержит от 1 до 40 символов; запрос принимает не более 20 элементов массива.
- Ключ имени формируется без учёта регистра через `toLocaleLowerCase('ru-RU')`; дубли удаляются с сохранением первого написания.

В [схеме Prisma](../../apps/api/prisma/schema.prisma) `TaskLabel` имеет уникальный ключ `(projectId, key)`. `TaskLabelAssignment` связывает задачу и метку составными внешними ключами с `projectId`, исключая назначение метки чужого проекта. Уже существующее имя сохраняет своё первое отображаемое написание. [resolveTaskLabels](../../apps/api/src/tasks/task-labels.util.ts) создаёт недостающие имена в одной транзакции с сохранением задачи. Неуспешный запрос и отмена формы не добавляют имена в каталог. Снятие меток и удаление задачи удаляют назначения, но сохраняют имена для повторного использования.

`GET /teams/:teamId/projects/:projectId/tasks/labels?search=текст` возвращает до 20 имён как `string[]`, упорядоченных по `key`. Необязательный `search` обрезает пробелы по краям и ограничен 100 символами; поиск ищет буквальную подстроку имени без учёта регистра, включая `%`, `_` и обратный слеш. Без непустого запроса возвращаются первые имена каталога. Доступ требует членства в команде и принадлежности проекта этой команде, как чтение задач.

Например, чтобы назначить две метки, передайте в PATCH:

```json
{ "labels": ["Backend", "Нужна проверка"] }
```

Для изменения правил имени используйте общую схему; разрешение имён и сериализация ответов находятся в `task-labels.util.ts`, запрос каталога — в `TasksService.findLabels`. Подключение выбора меток к форме описано в [frontend-сценарии задач](../frontend/task-workflow.md#форма-и-отправка).

## Логика поля `position`

### Создание задачи (`create`)

`POST /teams/:teamId/projects/:projectId/tasks` принимает необязательный `boardColumnId` по [createTaskSchema](../../packages/types/src/tasks/schemas/create-task.schema.ts). Можно выбрать колонку любой доски того же проекта; чужая или отсутствующая колонка даёт `404`. Если ID не передан, сервис выбирает системную колонку основной доски по `status`, по умолчанию `TODO`. Выбранная системная колонка определяет статус задачи; пользовательская сохраняет переданный статус или `TODO`.

`position` вычисляется автоматически внутри целевой колонки — явно передавать его не нужно.

```text
position = MAX(position WHERE projectId = ? AND boardColumnId = ?) + 1
```

Если в целевой колонке ещё нет задач (`MAX = null`), начальная `position = 1`. Это расчёт при создании, а не индекс вставки операции перемещения.

Создание выполняется в транзакции с блокировкой доски через `FOR UPDATE`: после блокировки сервис повторно проверяет целевую колонку, вычисляет максимальную позицию и создаёт задачу. Для изменения колонки вместе с полями задачи используйте [обычный PATCH](#обновление-задачи); для выбора позиции или переноса между досками — [API перемещения](#перемещение-задачи-movetask) с `expectedVersion`.

### Перемещение задачи (`moveTask`)

`PATCH /:taskId/move` принимает [MoveTaskToColumnDto](../../apps/api/src/tasks/dto/move-task-to-column.dto.ts): обязательные `fromColumnId`, `toColumnId`, `position` — индекс вставки с нуля — и `expectedVersion` из последнего ответа API. Дополнительно можно передать `priority` и `assigneeId`; `assigneeId: null` снимает назначение.

Перенос работает внутри колонки, между колонками и между досками одного проекта. Сервис транзакционно проверяет исходную и целевую колонки и версию задачи, пересчитывает порядок и версии затронутых задач. При переносе в системную колонку синхронизируется `status`; в пользовательскую — прежний статус сохраняется.

При конфликте исходной колонки или версии API возвращает `409`. После успешного переноса и после конфликта перечитайте затронутые доски, чтобы получить актуальные позиции и версии, включая соседние задачи. Клиент не должен отправлять отдельные запросы для пересчёта каждой соседней позиции.
