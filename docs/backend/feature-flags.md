# Флаги на API

API хранит состояния флагов, проверяет доступ к защищённым операциям и уведомляет клиентов об изменениях. Все endpoint-ы флагов требуют cookie-сессию; управление доступно только [разработчику системы](./system-developer.md).

## Хранение

| Модель                 | Назначение                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `FeatureFlag`          | Технический ключ, название, состояние, описание, ID создателя, плановый срок и даты |
| `FeatureFlagsRevision` | Общая версия снимка флагов                                                          |
| `FeatureFlagAudit`     | ID автора действия, действие, состояния до/после и версия изменения                 |

Изменение флага, запись аудита и увеличение версии выполняются одной транзакцией. Технический ключ уникален, неизменяем и остаётся зарезервированным после архивации.

Состояния — обычные записи БД: создание и управление ими не требуют миграций. Изменение схемы и отдельная подготовка данных для выпуска проходят через стандартный процесс миграций проекта.

## Подключение проверок

Технические ключи и реестр находятся в [`@repo/types`](../../packages/types/src/feature-flags/registry.ts). `FEATURE_REGISTRY` сопоставляет ключ понятному названию управляемого блока. `REQUIRED_FEATURE_KEYS` вычисляется из реестра и запрещает архивацию этих ключей.

Ниже условный пример: `NEW_SECTION` — новый ключ, который разработчик добавляет в существующие `FEATURE_KEYS` и `FEATURE_REGISTRY`.

Для контроллера или отдельного метода задайте требование:

```ts
import { Controller } from '@nestjs/common'
import { FEATURE_KEYS } from '@repo/types'
import { Authorization } from '../auth/decorators/authorization.decorator'
import { RequireFeatures } from '../feature-flags/feature.guard'

@Authorization()
@RequireFeatures(FEATURE_KEYS.NEW_SECTION)
@Controller('new-section')
export class NewSectionController {
	// Методы контроллера.
}
```

`@Authorization()` запускает JWT-проверку, затем `FeatureGuard`. Требования метода и контроллера объединяются; все перечисленные ключи должны быть включены. Для зависимого блока передайте также ключи его зависимостей.

В сервисных операциях проверку можно вызвать через `FeatureFlagsService.requireEnabled(key)`. Добавьте её до выполнения защищённого действия, включая обработчики вне HTTP-контроллеров, если на них должен распространяться флаг.

Guard читает PostgreSQL при запросе, без локального кэша. Выключенный, отсутствующий или архивированный ключ даёт `403` с `code: FEATURE_DISABLED` и `key`. Сбой БД не разрешает действие. Проверки членства, ролей и доступа к данным остаются обязательными. Отключение не отменяет уже начатые операции.

Реестр описывает подключение, но не анализирует исходники. Добавляйте запись вместе с проверками и выпускайте её на всех API перед включением флага. [Общий порядок подключения и архивации](../work/feature-flags.md).

## Контракт управления

Общие схемы запросов и ответов находятся в [`packages/types/src/feature-flags/index.ts`](../../packages/types/src/feature-flags/index.ts); Swagger использует эти схемы.

| Endpoint                          | Доступ                            | Назначение                                                              |
| --------------------------------- | --------------------------------- | ----------------------------------------------------------------------- |
| `GET /feature-flags/snapshot`     | Любой авторизованный пользователь | Снимок активных флагов: `key`, `enabled`, `updatedAt` и общая `version` |
| `GET /feature-flags/access`       | Любой авторизованный пользователь | Право текущего пользователя управлять флагами                           |
| `GET /feature-flags/events`       | Любой авторизованный пользователь | SSE-уведомления о версии снимка                                         |
| `GET /feature-flags`              | Разработчик системы               | Список с метаданными и архивом                                          |
| `POST /feature-flags`             | Разработчик системы               | Создание выключенной записи                                             |
| `PATCH /feature-flags/:id`        | Разработчик системы               | Изменение метаданных или состояния                                      |
| `POST /feature-flags/:id/archive` | Разработчик системы               | Необратимая архивация                                                   |
| `GET /feature-flags/:id/audit`    | Разработчик системы               | Последние 100 изменений в порядке убывания версии                       |
| `GET /feature-flags/server-time`  | Разработчик системы               | Текущее время API в ISO UTC                                             |

Создание принимает `key`, `title`, необязательные `description` и `expiresAt`; `enabled` в этом запросе запрещён. Новая запись всегда выключена, даже если её ключ уже зарегистрирован.

Для PATCH и архивации передайте `expectedVersion` из списка. Общая версия сериализует конкурентные записи; конфликт не меняет состояние и аудит. PATCH не позволяет изменить технический ключ.

Ответы управления содержат `connectedFeature` — название из реестра или `null`. Это вычисляемое поле, а не столбец БД. `required` показывает запрет архивации по реестру. Назначить подключение через запрос нельзя.

Включение разрешено только для зарегистрированного ключа. Метаданные неподключённой записи можно менять; ранее включённую неподключённую запись можно выключить. Во время выпуска с разными версиями API старый экземпляр может отклонять включение нового ключа — сначала обновите все экземпляры.

| Код   | Причина                                                                       |
| ----- | ----------------------------------------------------------------------------- |
| `401` | Нет действующей сессии                                                        |
| `403` | Нет права управления или проверяемый ключ не разрешает действие               |
| `404` | Неизвестный ID флага                                                          |
| `409` | Устаревшая версия, занятый ключ или запрещённая архивация/изменение архива    |
| `422` | Некорректные поля, попытка включить неподключённый ключ или недопустимый срок |

Снимок имеет ETag; `If-None-Match` позволяет получить `304` без повторной передачи неизменённых данных.

## Плановый срок

`expiresAt` — напоминание, оно не меняет состояние автоматически. Новый или изменённый срок сравнивается с текущим временем API внутри транзакции. Прошедший срок возвращает `422` без изменения флага, аудита и общей версии.

Ранее сохранённый срок может уже пройти: его разрешено оставить при редактировании других полей. `null` очищает срок, отсутствие поля в PATCH сохраняет его.

`GET /feature-flags/server-time` возвращает `{ serverTime: ISO UTC }` с `Cache-Control: private, no-store`; клиент использует этот источник для ограничения выбора даты.

## Аудит и имена

`createdById` — создатель флага, `actorId` — автор конкретного действия. Ответы управления дополняют их `createdByName` и `actorName` из текущего `User.name`. Профили читаются одним запросом по уникальным ID, только поля `id` и `name`.

Для `bootstrap` возвращается «Система». При удалённом профиле или пустом имени возвращается `null`; ID и история сохраняются. Имя не записывается в `before`/`after`, поэтому отображается текущее имя профиля. Поля имён необязательны в клиентском контракте; API возвращает их в ответах управления. Обычный снимок не содержит авторов и других метаданных.

## Уведомления между экземплярами

После успешной транзакции API публикует версию в Redis Pub/Sub. Все экземпляры уведомляют свои SSE-соединения событием `feature-flags-changed`; клиент заново получает снимок из API.

При подключении сервер отправляет текущую версию БД. Дополнительная сверка версии каждые 5 секунд восстанавливает уведомления при разрыве Redis или пропущенной публикации. PostgreSQL остаётся источником состояния; обычная доставка происходит после завершения транзакции, восстановление после пропуска — при следующей сверке.

SSE использует HttpOnly access-cookie. Heartbeat каждые 15 секунд повторно проверяет JWT и существование аккаунта. При истечении токена сервер отправляет `session-expired` и закрывает поток; клиент обновляет сессию и переподключается. Соединения и таймеры очищаются при отключении.

Все экземпляры API используют одну БД, один Redis и одинаковую настройку разработчика. Proxy должен пропускать `text/event-stream` без буферизации и поддерживать длительные соединения.
