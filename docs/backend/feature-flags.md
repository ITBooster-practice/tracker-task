# Runtime feature flags

## Хранение и миграция

`FeatureFlag` содержит технический `key`, отображаемый `title`, `enabled`, описание, автора, срок временного флага и даты. Флаги создаются и изменяются как записи, без миграции схемы. Миграции нужны при изменении структуры таблиц.

Применение: `pnpm prisma:db:update` (в Docker: `prisma migrate deploy --config prisma.config.mjs`). Миграция аддитивная: не меняет таблицы пользователей, команд, проектов и задач. Она также создаёт начальные `projects`, `tasks`, `boards`, `team-settings` со значением true, соответствующим текущим значениям по умолчанию Docker/stage. Если раньше функции выключались env-переменными, установите нужные значения в БД перед открытием обновлённого приложения пользователям. Повторный migrate deploy не перезаписывает переключатели. Общий seed/reset не нужен.

`FeatureFlagsRevision` хранит общую версию снимка; `FeatureFlagAudit` — автора, действие, старое/новое состояние и версию изменения. Флаг, аудит и версия изменяются одной транзакцией.

## API

Все endpoint-ы требуют cookie-сессию. Любой авторизованный пользователь читает `GET /feature-flags/snapshot` и `GET /feature-flags/access`. Снимок содержит только key/enabled/updatedAt и общую version. Ответ имеет ETag; If-None-Match возвращает 304 при неизменном снимке.

Только разработчик системы получает список с архивом (`GET /feature-flags`), создаёт (`POST /feature-flags`), меняет (`PATCH /feature-flags/:id`), архивирует (`POST /feature-flags/:id/archive`) и читает историю (`GET /feature-flags/:id/audit`, последние 100 изменений).

Для изменения и архивации требуется `expectedVersion` из полученного списка. Запись общей версии сериализует конкурирующие операции; устаревшая версия даёт 409 без изменения состояния и аудита. Неверные поля дают 422, неизвестный ID — 404, чужие права — 403. Технический key нельзя менять через PATCH. Создание дубликата, включая архивный ключ, даёт 409. Swagger описывает запросы и ответы на общих схемах `@repo/types`.

## Подключение и включение

Реестр `FEATURE_REGISTRY` находится в `packages/types/src/feature-flags/registry.ts`: технический ключ → название управляемой возможности. Здесь же объявлены `FEATURE_KEYS`; `REQUIRED_FEATURE_KEYS` вычисляется из ключей реестра и защищает подключённые флаги от архивации. Запись в реестре добавляется вместе с проверками в frontend/API, тестируется и проходит ревью. Она описывает подключение, но не анализирует исходники и не доказывает полноту защиты.

`GET /feature-flags` и ответы мутаций содержат `connectedFeature: string | null`: название из реестра или `null` для заготовки. Это вычисляемое поле, не столбец БД; изменить его запросом нельзя. Состояние `enabled` хранится отдельно и не означает, что флаг подключён.

`POST /feature-flags` принимает только `key`, `title`, необязательные `description` и `expiresAt`. Новая запись всегда создаётся с `enabled=false`, даже если её ключ уже зарегистрирован. Поле `enabled` в запросе создания отклоняется с 422.

`PATCH /feature-flags/:id` с `enabled=true` разрешён только для ключа в реестре запущенной версии API. Неподключённый ключ даёт 422 с пояснением; вся транзакция откатывается, включая описание, аудит и revision, уведомление не отправляется. Сохранять название/описание/срок заготовки и выключать ранее включённый неподключённый флаг можно. Подключённую функцию можно включать и выключать многократно; права на данные и зависимости других флагов сохраняются.

Для подключения создайте выключенную заготовку, добавьте проверки и запись в реестр, соберите `@repo/types`, выпустите frontend и все экземпляры API, обновите вкладки и список в панели. Только после этого включайте флаг. Сведения реестра меняются при выпуске кода, а не по SSE изменения значения; список можно перечитать кнопкой «Обновить». Во время смешанного выпуска старый API может отклонять включение нового ключа — дождитесь обновления всех экземпляров. Миграция БД для подключения не нужна; существующие значения флагов не сбрасываются.

## Плановый срок и время сервера

`GET /feature-flags/server-time` возвращает `{ serverTime: ISO UTC }` по часам экземпляра API. Доступен только разработчику системы, требует cookie-сессию, имеет `Cache-Control: private, no-store`. Ответ описан общей схемой `@repo/types` и Swagger.

При создании флага или изменении `expiresAt` API сравнивает полный момент UTC с текущим серверным временем внутри транзакции после блокировки версии. Прошедший срок возвращает 422: «Плановая дата и время не могут быть раньше текущего времени сервера». Состояние, аудит и общая версия остаются прежними. Это защищает и прямые запросы, независимо от часов клиента и UI.

Неизменённый ранее сохранённый срок может уже пройти: API разрешает сохранить его вместе с другими изменениями. Срок также можно убрать (`null`) или не передавать в PATCH. Новый срок должен удовлетворять ограничению сервера. Плановая дата не включает и не выключает флаг автоматически; миграция БД для этих проверок не требуется.

## Защита API

`@Authorization()` выполняет JWT-проверку до `FeatureGuard`. `@RequireFeatures(...keys)` задаёт требования контроллера и/или метода; требования объединяются. Флаги читаются непосредственно из PostgreSQL при запросе, без локального кэша. При выключенном, отсутствующем или архивированном флаге: HTTP 403 с `code: FEATURE_DISABLED` и key. Сбой БД не разрешает операцию.

- Все операции с проектами требуют projects.
- Все операции с задачами требуют projects и tasks; GET board дополнительно требует boards.
- Изменение/удаление команды, управление участниками и исходящими приглашениями требуют team-settings.
- Создание/просмотр команд, профиль, авторизация, просмотр/принятие входящих приглашений продолжают работать.

Проверки членства и ролей на данные остаются обязательными независимо от состояния флагов. Уже начавшиеся операции отключение не отменяет.

## Уведомления

`GET /feature-flags/events` открывает SSE для авторизованного браузера. После транзакции API отправляет событие в Redis Pub/Sub; все экземпляры API уведомляют свои соединения событием `feature-flags-changed`. Клиент повторно загружает snapshot, поэтому даже запоздалое событие не подменяет актуальные данные.

При подключении отправляется текущая версия БД. Каждый экземпляр API дополнительно сверяет её раз в 5 секунд: это восстанавливает уведомления при разрыве Redis, потерянной публикации или перезапуске процесса после commit БД. PostgreSQL остаётся источником истины. Обычная доставка происходит сразу после commit; при пропуске события восстановление занимает до 5 секунд плюс время запросов и сети.

SSE использует существующую HttpOnly access-cookie, без токенов в URL. Heartbeat отправляется раз в 15 секунд с повторной проверкой JWT и существования аккаунта. При истечении access-токена сервер отправляет `session-expired` и закрывает поток; клиент обновляет сессию через существующий auth-flow и переподключается. Таймеры и подписки удаляются при отключении клиента и остановке API.

Proxy должен пропускать `text/event-stream` без буферизации и поддерживать длительные соединения. Проверяйте поток через Caddy на stage, включая переподключение. Все экземпляры API используют одну БД, один Redis и одинаковую настройку разработчика.

## Жизненный цикл

Отсутствующий, выключенный или архивированный флаг закрывает функцию. Архивирование не превращает функцию в постоянную. Технический ключ неизменяемый и остаётся зарезервированным после архивации; отображаемые названия могут повторяться.

Ключи, на которые ссылаются поддерживаемые версии кода, перечисляются в `REQUIRED_FEATURE_KEYS` в `@repo/types`. Их архивирование запрещено. Для переименования технического ключа создайте новый флаг, переведите проверки в коде и завершите поддержку старого ключа.

Выпуск завершённой функции: включить её → удалить проверки и старую ветку кода на frontend/backend → удалить запись из `FEATURE_REGISTRY` и константу ключа → проверить и выпустить обновление → обновить старые открытые вкладки и завершить поддержку старых образов → архивировать флаг. Авторизацию и права на данные сохраняют. Для следующего обновления создаётся новый технический ключ, например `boards-redesign-v3`; название может быть прежним.

Право управления: [разработчик системы](./system-developer.md).
