# Модель досок и колонок

Доски принадлежат проекту: `Project → Board → BoardColumn → Task`. В проекте может быть несколько досок, у каждой — свой набор колонок.

## Сущности и ограничения

| Сущность      | Поля и ограничения                                                                                                                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Board`       | UUID `id`, `projectId`, `name`, `isDefault` (по умолчанию `false`), `createdAt`, `updatedAt`. Имя уникально внутри проекта: `[projectId, name]`.                                                                                     |
| `BoardColumn` | UUID `id`, `boardId`, `projectId`, строковые `key` и `title`, целочисленная `position`, `isSystem` (по умолчанию `false`), `createdAt`, `updatedAt`. Ключ и позиция уникальны внутри доски: `[boardId, key]`, `[boardId, position]`. |
| `Task`        | Необязательный `boardColumnId`. Индекс `[boardColumnId, position]` поддерживает чтение задач колонки по порядку. Поля `status`, `position` и прежний индекс `[projectId, status, position]` сохранены.                               |

`BoardColumn.projectId` повторяет проект доски для проверки принадлежности на уровне БД. Составные внешние ключи `[boardId, projectId] → Board[id, projectId]` и `[boardColumnId, projectId] → BoardColumn[id, projectId]` запрещают привязать колонку или задачу к чужому проекту. Для целевых пар добавлены уникальные ограничения `[id, projectId]`.

Удаление проекта каскадно удаляет его доски, колонки и задачи. Удаление доски удаляет её колонки, но внешний ключ задачи с `ON DELETE NO ACTION` блокирует удаление занятой колонки или доски. Сначала требуется перенести задачи; они не удаляются и не теряют связь автоматически.

Ключ колонки — строка, поэтому схема допускает пользовательские колонки.

## Применение схемы и совместимость

Миграция `20261027000000_add_boards_and_columns` добавляет таблицы, индексы, внешние ключи и nullable `Task.boardColumnId`. Она не меняет существующие задачи и не требует сброса БД или seed. Применять её нужно перед запуском API, собранного с обновлённым Prisma Client:

```bash
pnpm --filter api prisma:db:update
```

Для контейнерного API миграции должны входить в образ и применяться к БД перед запуском новой версии. Общие правила — в [инструкции Prisma](./prisma/README.md).

Миграция не создаёт default-доски и системные колонки и не заполняет `boardColumnId` существующих задач. Делать связь обязательной можно после backfill и обновления всех путей создания задач: нынешний CRUD ещё создаёт задачи без колонки.

Публичный [Tasks API](./tasks.md) работает через `status` и `position`. Его запросы явно исключают внутренний `boardColumnId` из ответа.

## Проверки

```bash
pnpm --filter api exec prisma validate
pnpm --filter api prisma:generate
pnpm --filter api test
```

Интеграционные проверки требуют отдельной тестовой PostgreSQL с применёнными миграциями:

```bash
pnpm --filter api test:e2e board-schema.e2e-spec.ts
```

`board-schema.e2e-spec.ts` проверяет несколько досок, уникальность имён/ключей/позиций, изоляцию проектов, сохранение занятой колонки, каскадное удаление проекта и совместимость существующего CRUD. Тесты создают собственные проекты и удаляют только свои данные; Redis им не нужен.
