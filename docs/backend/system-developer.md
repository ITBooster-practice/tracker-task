# Разработчик системы

Право управления флагами принадлежит одному существующему аккаунту, указанному в серверной настройке `SYSTEM_DEVELOPER_USER_ID`. Роли `OWNER`, `ADMIN` и `MEMBER` в командах этого права не дают. Пустая настройка закрывает управление для всех.

## Настройка

Войдите под нужным аккаунтом, откройте **Личный кабинет** (`/profile`) и скопируйте **ID пользователя** кнопкой рядом со значением. В настройке используется ID пользователя, не email и не ID команды.

| Окружение                        | Где задать `SYSTEM_DEVELOPER_USER_ID=<User.id>` |
| -------------------------------- | ----------------------------------------------- |
| Локальная разработка, `pnpm dev` | `apps/api/.env`                                 |
| Локальный Docker, `pnpm local`   | `apps/api/.env.local`                           |
| Stage                            | `/opt/tracker/stage/.env.stage`                 |

После изменения перезапустите API. Для локального Docker пересоздайте контейнер:

```sh
docker compose -f docker-compose.local.yml up -d --force-recreate api
```

Для stage выполните из каталога установки:

```sh
docker compose --env-file .env.stage -f docker-compose.stage.yml up -d --force-recreate api
```

Значение должно совпадать на всех экземплярах API. Оно хранится в окружении сервера, не в поле роли пользователя и не в публичных `NEXT_PUBLIC_*` переменных.

## Проверка доступа

Управляющие endpoint-ы сначала проверяют сессию через `JwtGuard`, затем аккаунт через `SystemDeveloperGuard`. Guard сравнивает ID авторизованного пользователя с серверной настройкой. Неавторизованный запрос получает `401`, другой аккаунт — `403`.

Регистрация, редактирование профиля и параметры запроса не назначают это право. Панель доступна на `/admin/feature-flags`; [порядок работы с флагами](../work/feature-flags.md).
