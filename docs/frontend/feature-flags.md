# Флаги на frontend

Frontend загружает снимок из API, использует его для отображения интерфейса и обновляет открытые клиенты по уведомлению сервера. [Создание, включение и архивация флагов](../work/feature-flags.md), [контракт API](../backend/feature-flags.md).

## Подключение проверок

Ключ должен быть объявлен в [общем реестре](../../packages/types/src/feature-flags/registry.ts) вместе с проверками. В примерах `NEW_SECTION` обозначает новый ключ разработчика.

Для проверки доступа используются следующие средства. React-проверки работают внутри `FeatureFlagsProvider`; серверная проверка получает снимок отдельно:

| Средство                    | Когда использовать                                    |
| --------------------------- | ----------------------------------------------------- |
| `useFeature(key)`           | Условное отображение отдельного элемента в React      |
| `hasFeature(snapshot, key)` | Проверка снимка, например при построении меню         |
| `FeatureGate`               | Раздел с состояниями загрузки, ошибки и недоступности |
| `requireServerFeature(key)` | Серверная страница или layout, в том числе прямой URL |

Для открытого раздела:

```tsx
import { FEATURE_KEYS } from '@repo/types'

import { FeatureGate } from '@/features/feature-flags'

export function NewSectionView() {
	return (
		<FeatureGate feature={FEATURE_KEYS.NEW_SECTION}>
			<section>Содержимое раздела</section>
		</FeatureGate>
	)
}
```

На серверной странице или в layout до возврата содержимого вызовите:

```ts
import { FEATURE_KEYS } from '@repo/types'

import { requireServerFeature } from '@/shared/lib/feature-flags/server'

await requireServerFeature(FEATURE_KEYS.NEW_SECTION)
```

Серверная проверка возвращает `404`, если ключ не включён. `FeatureGate` дополнительно закрывает уже открытый раздел после обновления снимка. Для отдельного элемента используйте `useFeature` из `@/shared/lib/feature-flags/context`, для меню — `hasFeature` из `@/shared/lib/feature-flags/feature-flags`.

Отсутствующий ключ не разрешает отображение. Если есть зависимости от других флагов, задайте их в `hasFeature` и соответствующих требованиях API. Скрытие элемента интерфейса само по себе не блокирует запрос к API.

## Загрузка и обновление

`FeatureFlagsProvider` хранит снимок и статус в TanStack Query и предоставляет React-контекст. Снимок загружается существующим Axios-клиентом с cookie-сессией и refresh-flow; общие схемы `@repo/types` проверяют ответ. ETag позволяет использовать прежний снимок при `304`.

SSE передаёт номер версии. При новой версии provider отменяет устаревшую загрузку, получает снимок и обновляет список/аудит панели. Повторные и старые версии не вызывают лишнего запроса.

После разрыва соединения или истечения JWT клиент восстанавливает сессию и переподключается с задержкой от 1 до 30 секунд. При размонтировании соединение и таймеры закрываются. После ошибки загрузки старый включённый снимок не разрешает отображение; `FeatureGate` предлагает повторить запрос.

Снимок не хранится в localStorage. Серверный кэш React ограничен одним render-запросом и не разделяет состояние между пользователями.

Изменение значения в БД приходит по SSE; новая запись в реестре приходит с выпуском кода. После выпуска обновите старые вкладки и перечитайте список в панели.

## Панель разработчика

Панель находится на `/admin/feature-flags`. Серверная страница и API проверяют право управления; ссылка в меню видна только разработчику системы.

Форма содержит технический ключ, название, описание и плановый срок. Создание всегда сохраняет выключенный флаг; редактирование отправляет только метаданные. Переключение выполняется кнопкой на карточке после подтверждения API, без оптимистического изменения.

Карточка показывает состояние и подключение отдельно. Название управляемого блока приходит в `connectedFeature` из реестра. При отсутствии подключения включение заблокировано; редактирование и архивация заготовки доступны. Зарегистрированные ключи архивировать нельзя.

| Карточка               | Граница    |
| ---------------------- | ---------- |
| Архивная               | Янтарная   |
| Не подключена          | Фиолетовая |
| Подключена и включена  | Зелёная    |
| Подключена и выключена | Обычная    |

Архивное состояние имеет приоритет над подключением, отсутствие подключения — над включённостью. Цветные границы без прозрачности, толщиной 1 px. Фон карточки также соответствует статусу: зелёный, янтарный или фиолетовый оттенок с учётом темы. У подключённого выключенного флага фон обычный.

История открывается после выбранной карточки, перед следующей. Открыта одна история; повторное нажатие или **Закрыть историю** закрывает её. Поиск и фильтр скрывают историю вместе с карточкой. Длинные строки JSON переносятся без горизонтальной прокрутки.

В карточках и истории отображаются имя и ID автора. Для системного автора — «Система», при отсутствии имени — «Имя недоступно» и ID. Имена приходят из API; общий список пользователей frontend не запрашивает.

При `409` панель обновляет список и предлагает повторить действие по свежим данным. При `403` управление закрывается. Создание и редактирование используют `DialogDrawer`: от 768 px — модальное окно, на меньшей ширине — Drawer снизу с прокруткой формы.

## Плановая дата

Форма использует `DateTimePicker` из `@repo/ui`: селекты месяца и года, ввод даты с клавиатуры, поле времени и выбор часов/минут. [Параметры и примеры компонентов](../../packages/ui/README.md#дата-и-время).

Минимум берётся из `GET /feature-flags/server-time`, обновляется раз в минуту и между ответами продвигается через `performance.now()`. Изменение часов компьютера на него не влияет. Пока время API не загружено или его обновление завершилось ошибкой, выбор новой даты заблокирован; доступен повтор запроса.

Для текущего дня минимальное время округляется вверх до допустимой минуты. Форма проверяет изменённый срок при сохранении; окончательную проверку выполняет API. Дата отображается в часовом поясе браузера и отправляется в ISO UTC. Неизменённый сохранённый срок передаётся с исходными секундами и миллисекундами, чтобы прошедшая дата не мешала редактированию других полей.

Плановая дата не переключает состояние флага автоматически.

## Окружение

Серверные запросы web в Docker используют `API_INTERNAL_URL=http://api:3000`, браузер — публичный `NEXT_PUBLIC_API_URL`. Внутренний URL не попадает в bundle; cookie-сессия и проверки API сохраняются.

[`apps/web/.env.example`](../../apps/web/.env.example) — образец настроек, Next.js сам его не загружает. Для локального `next dev` используется `apps/web/.env.development`; корневой `pnpm dev` создаёт его при отсутствии и добавляет публичный адрес API, сохраняя существующие настройки. Файл исключён из Git.

Для stage и production `.env.development` не используется Next.js: публичный URL задаётся при сборке образа, внутренний — в окружении контейнера. Состояния флагов во всех окружениях хранятся в БД, а не в env-файлах.

Для разработки без API можно явно задать `NEXT_PUBLIC_FEATURE_FLAGS_DEV_FALLBACK=true` при `NODE_ENV=development`. Локальный снимок включает зарегистрированные ключи и показывается с предупреждением. В production, включая stage, режим недоступен; прав управления и обхода API он не предоставляет.
